# CLAUDE.md

Монорепозиторий **movier** — самохостируемая платформа для поиска, скачивания
и просмотра фильмов. Описание системы: `docs/project.md`.

## Карта репозитория

```text
apps/mobile/       Flutter-клиент (iOS + Android). Свой тулчейн, свой pubspec
apps/stream/       Spring Boot: TMDB, поиск раздач через Jackett, отдача HLS. API клиента
apps/downloader/   Spring Boot: торрент → FFmpeg/HLS → MinIO, Redis Streams
deploy/            docker-compose с инфраструктурой стека
docs/              документация уровня системы
```

Модульная документация лежит рядом с модулем: `apps/*/CLAUDE.md`,
`apps/*/docs/`. Читай её перед работой над соответствующим модулем.

Связь сервисов: `stream` публикует задачу в Redis-стрим `download:stream`,
`downloader` её забирает, скачивает и конвертирует, кладёт HLS в бакет
`content` MinIO и отвечает в `result:stream`, который слушает `stream`.
Схемы одной БД `movie` разведены: `film_stream` и `film_download`.

## Сборка и запуск

Бэкенд — один Gradle-проект с корневым wrapper'ом:

```bash
./gradlew :stream:bootRun        # порт 8084 — сюда ходит клиент
./gradlew :downloader:bootRun    # порт 8085
./gradlew build                  # оба модуля
```

Общие плагины, версии и зависимости — в корневом `build.gradle`
(блок `subprojects`). В `apps/*/build.gradle` только то, что уникально
для модуля. Единый тулчейн — JDK 24.

`apps/stream` требует переменные из `apps/stream/.env`
(`TMDB_API_TOKEN`, `JACKETT_API_KEY`) — файл не в git, шаблон
в `.env.example`.

Клиент:

```bash
cd apps/mobile && flutter pub get && flutter run
```

`apps/mobile` намеренно не включён в `settings.gradle` — Flutter собирает
свою Android-часть сам.

Инфраструктура (postgres, redis, minio + бакет `content`, jackett):

```bash
cd deploy && docker compose up -d
```

Приложения при локальной разработке ходят на `localhost` к этим сервисам,
в контейнерах не запускаются. Consumer-группы Redis сервисы создают сами.

## Соглашения

**Общение:** по-русски. Код, комментарии в коде, документация и коммиты —
по-английски.

**Коммиты:** Conventional Commits (`feat`, `fix`, `refactor`, `docs`,
`chore`). Если правка затрагивает один модуль, указывай его в scope:
`feat(downloader): ...`.

**Бэклог:** идею или задачу от пользователя записывай на русском в ишью с помощью gh в таком формате. Название ишью пиши на английском, чтобы была возможность создать ветку
*MODULE(ENG)* | [*TYPE(ENG)* (Task, Bug, Chore)] *Title*
Описание ишью должно содержать краткую мотивацию для чего это(1-2 коротких предложения)
Блок *Description* с описание задачи для агента/человека, как постановка задачи
Блок *Scope* с примерным описанием скуопа работ
Блок *Benchmark* с описанием(полученным от пользователя, запрашивай при необходимости) критерии приемки(может быть пустым)

## Критические правила

**Перед нетривиальной работой** прочитай этот файл и docs модуля,
который правишь.

**После изменения API или схемы БД** обнови документацию модуля.

**Контракт клиент — бэкенд.** Правка DTO в `apps/stream` и модели
в `apps/mobile/lib/**` — одно изменение, делай их вместе

**Контракт stream — downloader.** Формат сообщений в `download:stream`
и `result:stream` правь с обеих сторон одним изменением.

**Секреты.** Токены и ключи только через переменные окружения
(`${TMDB_API_TOKEN}`, `${JACKETT_API_KEY}`), никогда не хардкодь
их в `application.yml`.

### Перед написанием кода

Тривиальные правки (опечатки, однострочники, переименования) — делай сразу.

Для всего остального не начинай реализацию, пока не закрыты вопросы:

1. Оспорь подход — назови изъяны, упущенные краевые случаи, риски
   безопасности. Прямо, без вежливых обёрток.
2. Спроси про неизвестное — если что-то неоднозначно, спрашивай, не угадывай.
3. Предложи альтернативы — если есть проще или надёжнее, скажи и объясни.
4. Перечисли краевые случаи: конкурентный доступ, пустой вход, большие
   объёмы, нехватка прав, откат миграции и др.
5. Дождись подтверждения — не пиши код, пока план явно не одобрен.
6. Если план оформлен, то предложи пользователю сформировать ишью как бэклог

### Общее

- Делай только то, о чём попросили. Не рефактори соседний код, не комментируй
  то, что не менял, не вводи абстракции под гипотетическое будущее.
- Никогда не редактируй генерируемые файлы: `*.g.dart`, `*.freezed.dart`
  (меняй исходник и запускай `build_runner`), MapStruct `*Impl`
  в `build/generated`.
- Миграции Flyway не правь задним числом — добавляй новую.
- Говори прямо. Указывай на плохие идеи. Возражай, когда есть основание.
  Цель — правильная реализация, а не быстрая.
